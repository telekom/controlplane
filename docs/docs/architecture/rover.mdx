# Rover Domain

The Rover domain is the primary user-facing entry point for the Control Plane. Users define their API exposures, subscriptions, and event configurations in a declarative **Rover file**, and the operator translates them into resources across multiple other domains.

## Entry Points

Users interact with the Rover domain through three paths:

| Path | Description |
| ---- | ----------- |
| **Rover-CTL** | Command-line tool. Reads a local Rover file and sends it to the Rover Server. |
| **Rover Server** | REST API. Validates the configuration, uploads specifications to the File Manager, obfuscates secrets through the Secret Manager, and creates the Rover resource in Kubernetes. |
| **Direct kubectl** | Apply a Rover resource directly to the Kubernetes API (for advanced users or automation). |

### Resource Names and Labels

The Rover Server accepts resource names between 2 and 90 characters. Names longer than 63 characters retain their full resource name, while the `cp.ei.telekom.de/application` label is shortened to fit Kubernetes' 63-character label-value limit. The shortened value retains the beginning and end of the name, with a deterministic hash in the middle.

The server also normalizes the environment, team, and group labels to lowercase, replaces spaces, underscores, and slashes with hyphens, trims leading and trailing hyphens, and shortens values exceeding the label-value limit.

## Domain Interactions

- **Application domain** — Creates Application resources.
- **API domain** — Creates Api, ApiExposure, and ApiSubscription resources.
- **Event domain** — Creates EventExposure and EventSubscription resources.
- **File domain (SFTP)** — Creates the SFTP user (shared space) from a `FileSpecification` and registers producer/consumer SSH public keys for `fileType` exposures and subscriptions. Gated behind the `file` feature flag.
- **Gateway domain** — Configures traffic management settings.
- **Identity domain** — Configures authentication settings.
- **Approval domain** — Integrates approval requirements for exposures.

## File Types (SFTP)

Rover can configure an external SFTP file-transfer service without changing the customer-facing Rover file:

- A `FileSpecification` defines a `spec.type` (e.g. `dds-rc1-provider-file`), its `spec.version`, and a description. It can also include an optional YANL schema in `spec.specification`; Rover Server stores that document in File Manager and returns it through the FileSpecification API. Its metadata name must be the normalized type (lowercase, dots replaced by hyphens).
- Apply FileSpecifications through Rover-CTL like other Rover resources; Rover Server persists the resource and the Rover controller creates the matching file-domain `FileType`.
- A `fileType` **exposure** (producer) or **subscription** (consumer) with `variant: sftp` and one or more `publicKeys` registers those SSH keys on the matching SFTP user.

### apiVersion

`ApiRoadmap`, `ApiChangelog`, and `FileSpecification` accept both `tcp.ei.telekom.de/v1` and `rover.ei.telekom.de/v1` API versions. Existing manifests using `tcp.ei.telekom.de/v1` remain supported.

```yaml
apiVersion: rover.ei.telekom.de/v1
kind: FileSpecification
metadata:
  name: invoice-monthly
spec:
  type: invoice.monthly
  version: 1.0.0
  description: Monthly invoice exports
  specification:
    type: object
    properties:
      invoiceId:
        type: string
```

:::warning
Rover-CTL resolves handlers by the `apiVersion`/`kind` pair. A file with an unknown combination is skipped silently — `apply` logs `Handler not found. Ignoring...` and still exits with code `0`.
:::

Validation rules enforced by the Rover webhook:

- `fileType` exposures/subscriptions are only allowed on the `cetus` and `canis` zones.
- `variant: sftp` is optional.
- At least one public key is required; both the key `label` and `key` value must be unique per `fileType`.

Because file transfer happens directly over SFTP, a Rover that only exposes/subscribes to file types yields a **logical** Application (`needsClient` and `needsConsumer` are `false`). If the same Rover also has an API or event subscription, a client is still required.

## Rover and Application Info Pagination

`GET /rovers` and `GET /rovers/info` read one page per request. The default and maximum `limit` are **20**; the minimum is **1**. Follow `_links.next` until it is empty to retrieve subsequent pages. Continuation URLs retain the page size and encode the cursor. Authorization scope is enforced on every request; application-info listing requires a team client.

For `GET /rovers/info?names=app-a&names=app-b`, the server directly looks up the named Rovers in the caller's team. Up to **100 names** are accepted, duplicates are returned once, and missing names are skipped. All matches are returned in name order without pagination links. In this mode, `limit` and `cursor` do not affect selection, although supplied query values must still pass validation.

`roverctl get-info` follows application-info continuation links automatically when no names are supplied. Explicit-name lookups use a single request. Other endpoints retain their existing page-size limits. The `sort` and `shallowInfo` behavior is unchanged by this pagination update.

`roverctl` does not call the scheme, host or path of a `next` link. It rebuilds each follow-up request from the original request URL, keeps that request's query parameters, and takes only `cursor` and `limit` from the link. A link without exactly one non-empty `cursor`, with an invalid `limit`, or with a malformed URL or query fails with a fixed reason; the link itself is not printed. Values passed as a cursor that are not `http(s)://` URLs are sent unchanged as opaque cursors.

### Pagination links behind a gateway prefix

Rover Server builds `_links` from the scheme and host of the incoming request, as reported by the web framework (which honours `X-Forwarded-Host` and `X-Forwarded-Proto`).

For the path, links use the `requestPath` claim from the authenticated JWT, preserving gateway prefixes such as `/rover/api`. The token issuer is responsible for providing the correct public request path.

- The claim is used whether or not Last-Mile Security (LMS) validation is enabled. LMS validation is disabled by default.
- If the claim is missing, empty or not a string, links use the incoming request path. Requests without JWT authentication, including internal-listener and mock-authentication requests, also use the incoming path.

When `listeners.external.jwt.lms.basePath` is set, the JWT middleware additionally checks that `requestPath` equals that base path plus the incoming request path and that `operation` matches the request method. These comparisons ignore case; mismatches are rejected before reaching the handlers. Each listener supports one configured LMS base path.
