# Admin Domain

The Admin domain manages the foundational infrastructure of the Control Plane — environments, zones, and remote organizations (planned feature). These resources define *where* applications are deployed and *how* different cloud environments are connected.

This domain is typically managed by platform administrators, not application teams.

## Zone Provisioning

When a Zone is reconciled, the Admin operator bootstraps everything the zone needs to operate — so administrators no longer have to create these building blocks by hand. This includes the identity realms and the gateway admin client described below.

### Readiness semantics

A Zone remains not ready until its initial managed sub-resources are ready. Once initial provisioning succeeds, `Ready=True` is latched and represents successful provisioning rather than continuous aggregate child health. Later child degradation, child updates, and Zone spec changes do not clear it; the operator reports each child observed as not ready during reconciliation through a Warning event on the Zone. Reconciliation errors continue to use the normal controller error handling.

### Provisioning order

The Admin operator creates the identity provider and the two identity realms first. It waits until all three report `Ready=True` before creating the clients, gateway resources, and routes that depend on them. This prevents requests from reaching the identity provider before the realms are active.

While it waits, the Zone reports `Ready=False` with reason `SubResourceNotReady` and names the resource that is not ready. Changes to that resource automatically trigger another reconciliation. Once the Zone has completed its initial provisioning, this readiness check no longer blocks later updates.

### Identity realms and the rover client

Each zone gets two identity realms in its identity provider:

- A **default identity realm** (named after the environment) — used for normal API consumers and providers. It carries the zone's token claims (`originZone`, `originStargate`, `clientId`).
- An **internal `rover` realm** — used only for admin-config clients that the platform itself needs.

Inside the internal realm, the operator creates the **`rover` client** — the OAuth2 client the Gateway operator uses to authenticate against the gateway's admin API (its issuer is `…/auth/realms/rover`).

The Admin operator manages exactly one `rover` client per Zone, shared by all of its gateways, including those serving AI traffic. Each Zone must use its own backing identity provider; clients are not shared across Zones. Provisioning is automatic and cannot be disabled. Administrators configure gateway admin endpoints and their identity provider association, but cannot override the gateway admin client ID or secret through the Zone.

The client is managed independently of individual gateways. Reconciliation preserves an existing client's secret while updating its non-secret settings, so adding or reordering gateways does not rotate credentials. Gateways receive the shared credentials only after the client resource has been created or updated successfully.

With **Secret-Manager enabled**, the secret is stored at the stable environment-scoped path `zones/<zone>/admin/rover/clientSecret`. The identity Client and Gateway resources hold secret references rather than the value. If the client resource is missing, provisioning reuses the stored secret and generates a new one only when Secret-Manager confirms that no value exists. Lookup failures are retried, not treated as permission to generate replacement credentials. A secret stored before a failed client creation is reused on retry.

With **Secret-Manager disabled**, credentials are kept inline on the client and gateways. Reconciliation still preserves an existing client's secret, but recreating a manually deleted client generates a new one. With Secret-Manager enabled, recreation reuses the stored value instead.

Zone deletion deliberately retains the client and its stored secret; deleting the Client resource would also delete the backing identity-provider client. Run the Admin operator with leader election when using multiple replicas to prevent competing provisioning attempts.

Every named gateway exposes issuer, certificate, and OpenID discovery routes for the default realm and the internal `rover` realm, plus the team-api realm when configured. These routes cover the hostnames and base paths of all presets using that gateway. World-visible zones add `/spacegate` after the preset base path.

Admin also creates an owned `<gateway>--zone-health` passthrough route for every gateway, independent of managed routes and DTC. It covers every preset hostname and base path without `/spacegate`. Its `spec.traffic.healthProbe: true` flag tells Gateway to answer HEAD probes with 200 without contacting an upstream. The Route CRD gains this optional boolean; the Zone CRD is unchanged. Shared preflight validation checks the 20-hostname and 10-distinct-path Route limits before creating identity or health routes. Stale-route cleanup removes health routes when their gateway is removed.

Zone admission and reconciliation share aggregation, normalized path construction, and cardinality validation in `admin/internal/routeinputs`. Create/update admission rejects excessive inputs with field-specific errors; the controller retains a defensive blocked-error check for existing invalid Zones. Fixed identity and health suffixes preserve the number of distinct normalized base paths, so validation does not depend on provisioned realm names or visibility.

### Secret onboarding (defaulting webhook)

A Zone **defaulting webhook** processes a zone's sensitive fields before the resource is stored — the IDP admin password and the Redis password. The gateway admin (`rover`) client secret is managed separately during Zone provisioning, as described above.

- **When Secret-Manager is enabled**, the webhook uploads each value to Secret-Manager under a `zones/<zone>/admin/...` path and replaces the clear-text value in the Zone with a secret **reference**.
- **When Secret-Manager is disabled**, the same secrets are generated **inline** and kept on the resource.

Either way, you can leave a secret field empty to have one generated for you, or set it to the `rotate` keyword to force a new value. On updates, omitting a secret preserves the existing one, so re-applying a Zone never regenerates secrets by accident.

See [Secret Manager Domain](./secret-manager.mdx) for how references are stored and resolved, and [Admin Journey: Environments & Zones](../admin-journey/environments-and-zones.md#zone-secrets) for the operator-facing guide.

## Domain Interactions

- **Gateway domain** — Zones define which gateway instance is used. The Gateway operator reads the zone's gateway configuration (presets, URLs, features) when provisioning routes. Managed routes (TeamAPI and Proxy) are created directly by the zone handler.
- **Identity domain** — Zones define which identity provider is used. The Identity operator reads the zone's IDP configuration when provisioning clients and realms. The zone handler creates a default identity realm with token claims (`originZone`, `originStargate`, `clientId`) and the internal `rover` realm (with the `rover` gateway admin client) for admin-config clients.
- **Organization domain** — Teams are created within environments. Zones determine where team resources are provisioned. If a zone has TeamAPI-type managed routes, a team-api identity realm is created for team-facing APIs.
- **Event domain** — EventConfig resources reference zones for event routing and meshing.
- **Secret Manager domain** — The Zone defaulting webhook onboards zone secrets (IDP admin password, Redis password) and stores references instead of clear-text values.
